# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

The repository root has no top-level app yet (just this file and a placeholder `README.md`). The only real code lives in `nhl_toolkit/`, a Python toolkit now spanning Phase 1 (schedule ingestion + travel/rest metrics) and Phase 2 (odds ingestion, the generic policy-driven scoring engine, and the daily full-slate picks report). There is no test suite yet — dependencies are managed by hand (`pip install requests pyyaml`; everything else is stdlib).

Use a repo-root `.venv` (not a per-subdirectory one) even though `nhl_toolkit/` is the only Python code today — see `.gitignore` (`.venv/`, `*.db`, `.env`, and `nhl_toolkit/reports/` are excluded from version control).

`betting-toolkit-design.md` (repo root) is the full project design doc — read it before planning any new work here. It lays out the end goal: a scheduled, no-LLM Python pipeline that fetches NHL schedule/odds/injury/travel data into a database, scores every game through a config-driven weighted policy engine (`policy.yaml`), outputs a daily picks report ranking every game by edge, and logs outcomes for backtesting. `nhl_toolkit/` now covers build-order steps 1–7 of that design (arenas, schedule ingestion, travel/rest metrics, odds ingestion, the policy engine, the daily report/`picks_log`, and grading) — only the `injuries` table and the ROI/weight-tuning analysis remain design-only.

Odds ingestion requires a free API key from https://the-odds-api.com, stored as `export ODDS_API_KEY=...` in a repo-root `.env` (gitignored, never commit it) and loaded with `source .env` before running `lib/fetch_odds.py`.

## Commands

Run all commands from `nhl_toolkit/`. Entry-point scripts you run directly live in `bin/`; everything they import lives in `lib/`.

```bash
pip install requests pyyaml                                # third-party dependencies

source .env && python bin/run_daily.py --date 2026-10-01   # run the full pipeline for one date and build its report
```

`bin/run_daily.py` is the normal way to produce a day's report: it runs every step below in order (fetching just that date's game-week, so it's cheap even run daily) and skips the odds step gracefully if `ODDS_API_KEY` isn't set. As its last step it also commits and pushes any changed `docs/` files to `origin/main` (pass `--no-push` to skip this, e.g. for a local test run you're not ready to publish). Each stage can also be run standalone:

```bash
python lib/db.py                                           # create nhl.db + schema (also runs automatically from every script below)
python lib/fetch_schedule.py --start 2026-10-01 --end 2026-10-31   # upsert schedule/scores for a date range (defaults to today's game week)
python lib/grade.py                                         # grade any newly-final picks_log rows (result + straight_up_result)
python lib/travel_metrics.py                               # rebuild schedule_context (rest/travel/timezone metrics) from `games`
python lib/metrics.py                                      # bridge schedule_context into the generic metrics/metric_values schema
python lib/form_metrics.py                                 # rebuild recent_form/goal_differential metric_values from `games` scores
source .env && python lib/fetch_odds.py                    # append an odds snapshot per (game, bookmaker) from The Odds API
python lib/market_metrics.py                                # derive market_edge metric_values from odds on record
python lib/score.py --date 2026-10-01                       # apply policy.yaml to metric_values -> daily_scores
python lib/report.py --date 2026-10-01                      # rank every game by score gap, print/write CSV + HTML, log to picks_log
python lib/backtest.py                                      # not part of run_daily.py -- a manual tuning aid, see below
```

`fetch_schedule.py` is an upsert and safe to re-run daily to pick up final scores. `travel_metrics.py`, `metrics.py`, and `form_metrics.py` fully delete-and-rebuild the metric_values rows they own each run — always re-run them in order (`travel_metrics.py` then `metrics.py`/`form_metrics.py`, either order between those two) after `fetch_schedule.py`, since none of them rebuild automatically (`run_daily.py` handles this ordering for you). `fetch_odds.py` only appends (never deletes), so re-running it accumulates a quote history rather than duplicating in an upsert sense. `market_metrics.py` fully delete-and-rebuilds like `travel_metrics.py`/`metrics.py`/`form_metrics.py` do, but always from whatever's currently in `odds` regardless of whether `fetch_odds.py` ran this time — run it after `fetch_odds.py` and before `score.py`. `score.py` and `report.py` are each idempotent per `(date, policy_version)` — rerunning replaces that date's rows rather than duplicating them. `grade.py` only touches `picks_log` rows that are still ungraded (`result IS NULL OR straight_up_result IS NULL`), so it's safe to re-run as often as you like and never re-grades or overwrites an already-graded row. (All of these live under `lib/`.)

`report.py` writes three outputs: a local CSV (`nhl_toolkit/reports/`, gitignored), a static HTML page (`docs/reports/picks/picks_{date}.html`, git-tracked), and a regenerated `docs/index.html` linking every report newest-first. If `target_date` is actually today, it also writes `docs/reports/picks/current.html` — a byte-identical copy at a stable filename, so a bookmarked/shared URL always shows the latest picks without the date in it. (A real symlink would be more "correct" but doesn't survive a GitHub Pages build, which runs in Jekyll's safe mode and ignores symlinked files; a duplicated file is the static-hosting-safe equivalent.) `current.html` is only ever written when rendering *today's* actual report — the full-history refresh loop in `run_daily.py` re-renders every past date too, and must never clobber it with stale content. `docs/index.html` links to it as "Today's Picks" whenever it exists. The `docs/` folder is meant to be served via GitHub Pages (repo root or `/docs` on `main`) and is now live at https://babruzi.github.io/hockey-web/ (repo was made public to enable free-tier Pages).

`policy_page.py` renders `docs/reports/policies/policy.html`, a reference table of every metric in `policy.yaml` (weight, normalize method, description/unit from the `metrics` catalog) — linked from the reports index, meant to make weight-tuning easier without opening the YAML. It reads `policy.yaml` directly each time, so it's always current; nothing needs to be kept in sync by hand. `run_daily.py` regenerates it every run. `docs/reports/` has two subdirectories: `picks/` (one HTML page per scored date) and `policies/` (currently just the one current-policy reference page — a natural place for a per-`policy_version` history later, but nothing writes one yet).

### Running this daily / accumulating a season's data

`nhl.db` is meant to be a long-lived, ever-growing local database, not something reset between runs — nothing in this pipeline drops or replaces the whole DB (`*.db` is gitignored deliberately; GitHub is for code backup only, not data). One-time backfill for a season already in progress, then run daily from there:

```bash
python lib/fetch_schedule.py --start 2026-10-01 --end 2026-10-31   # backfill however far the season has gotten
python bin/run_daily.py --date 2026-10-01                           # then run_daily.py daily going forward
```

`run_daily.py` re-fetches a trailing `--lookback-days` window (default 3) behind `--date` in addition to that date's game-week, so games that finished in the last few days get their final score upserted even after they're no longer "today" — without this, a game played yesterday would stay stuck at its pre-game state forever once `--date` moves past it. If you ever miss several days of runs, re-run the backfill command above to close the gap (upserts are idempotent, so overlapping ranges are harmless).

For unattended daily runs, `run_daily_cron.sh` is a cron-safe wrapper (absolute paths, sources `.env`, logs to `nhl_toolkit/logs/`, both gitignored):

```
0 9 * * * /Users/babruzi/Documents/VSCODE/GITHUB/hockey-web/nhl_toolkit/bin/run_daily_cron.sh
```

## Architecture

Data flows through a pipeline of scripts, each its own file under `nhl_toolkit/lib/`, all sharing one SQLite DB (`nhl_toolkit/nhl.db`). `nhl_toolkit/bin/` holds the two scripts meant to be invoked directly (`run_daily.py` and its cron wrapper); everything else is a `lib/` module that either gets imported by `run_daily.py` or run standalone for one pipeline stage.

**Phase 1 — schedule and travel:**
1. **`lib/db.py`** — owns the schema (all tables below). `games` is raw schedule/score data keyed by the NHL's own `game_id`. `schedule_context` is one row per `(game_id, team_id)` holding derived metrics (rest days, games in trailing 7/14/30 days, distance traveled, timezones crossed, back-to-back flag), FK'd to `games`.
2. **`lib/fetch_schedule.py`** — pulls from the NHL Web API (`api-web.nhle.com/v1/schedule/{date}`), which returns a ~7-day "game week" per call. Walks a date range one game-week at a time and upserts into `games` (`ON CONFLICT(game_id) DO UPDATE` on score/state/start-time — never inserts duplicates).
3. **`lib/travel_metrics.py`** — reads `games` per-team in chronological order and derives `schedule_context` by walking each team's game history once, carrying rolling state (previous venue, previous date, trailing played-dates window). Distance and timezone-shift math depends on `lib/arenas.py`.

**Phase 2 — odds, generic metrics, and policy-driven scoring:**
4. **`lib/metrics.py`** — bridges `schedule_context`'s fixed columns into the design doc's generic `metrics`/`metric_values` tables (one row per name in `metrics`, one row per `(game_id, team_id, metric_id)` in `metric_values`). This is what lets new scoring factors (injuries, recent form, odds movement) get added later as data instead of schema/code changes.
5. **`lib/form_metrics.py`** — derives four metrics straight from `games` (no separate context table needed): `recent_form` (win % over a team's last 10 completed games), `goal_differential` (average goal margin over that window), and `goals_for_avg`/`goals_against_avg` (average goals scored/allowed over the same window — added later to drive `report.py`'s Over/Under recommendation; `goal_differential` is exactly `goals_for_avg - goals_against_avg`, computed from the same rolling deques). Walks each team's full game history chronologically, but only updates its rolling window on completed games — **the NHL Web API marks a completed game's `game_state` as `"OFF"`, not `"FINAL"`** (the `games.game_state` column comment used to claim otherwise; that was wrong and silently broke this until it was caught by checking against a real, already-completed season's scores). A metric_values row is written for every game including future ones, using only games already played, so there's no lookahead into the game being scored. `goals_for_avg`/`goals_against_avg` initially weren't added to `policy.yaml` — `score.py` only applies weights for metric names explicitly listed there, so seeding a new metric into the `metrics` table never silently changes `total_score`/the Money Line pick unless you also weight it. `goals_against_avg` was added as a weighted metric (`-0.20`, zscore) once `backtest.py` showed it correlating with actual goal margin more strongly than `goal_differential` itself (policy_version `2026-10-v2`); `goals_for_avg` remains unweighted (its own correlation is much weaker). Note `goals_against_avg` and `goal_differential` aren't independent — `goal_differential` is literally `goals_for_avg - goals_against_avg` — so weighting both means the defensive component is counted twice in `total_score`, intentionally for now; `backtest.py`'s next read on `goal_differential`'s correlation after this change is worth checking for whether that overlap is helping or just adding redundant noise.
6. **`lib/fetch_odds.py`** — pulls moneyline/puck-line/totals from The Odds API (`icehockey_nhl` sport key) and appends snapshot rows to `odds`, one per `(game, bookmaker)` per run — it's an append-only time series, not an upsert, so re-running frequently is how line-movement gets tracked later. Captures a price for every market including `spreads` (`home_spread_price`/`away_spread_price`) — the feed always included this, it just wasn't read into the schema until `report.py` needed it for the puck-line's own price, not only the home/away moneylines. Since the feed identifies teams by full name, not abbrev, matching a quote to a `games` row goes through `arenas.TEAM_NAME_TO_ABBREV` and then a `(home_abbrev, away_abbrev, local_game_date)` lookup — the local date is computed by converting the feed's UTC `commence_time` into the home arena's timezone.
7. **`lib/market_metrics.py`** — derives a `market_edge` metric from `odds`: each team's devigged, market-implied win probability, computed from the moneyline (not the puck-line spread — NHL puck lines are fixed at 1.5 goals in every quote this pipeline has ever recorded, so a spread-based version of this metric is nearly a constant and carries almost no signal; the moneyline is where the market's actual opinion about *how much* it favors a team lives, e.g. a -218/+180 line vs. a -115/-105 line on an identical ±1.5 spread). Devigging means converting both sides' American odds to raw implied probabilities and dividing each by their sum, removing the bookmaker's overround so the two sides sum to exactly 1. Uses DraftKings' own moneyline (`PRIMARY_BOOK`, kept in sync with `report.py`'s copy of the same constant by hand to avoid a circular import) when it has posted one, falling back to a cross-book average of every bookmaker's devigged probability otherwise. This is what actually puts the betting market into the weighted scoring equation — previously `spread_at_pick` only fed `report.py`'s display and `grade.py`'s after-the-fact ATS grading, never `score.py`'s `total_score`. Fulfills the "market line movement (steam)" metric from `betting-toolkit-design.md`'s original starter catalog (section 5), left unimplemented until now. Like `recent_form`/`goal_differential`, a `(game, team)` pair with no odds quote simply gets no value rather than erroring. Needed no changes to `score.py`, `report.py`, or `backtest.py` — adding (and later reworking) it was purely a matter of writing to `metric_values` and adding a line to `policy.yaml`, which is exactly the point of the generic metrics schema.
8. **`policy.yaml`** (repo: `nhl_toolkit/policy.yaml`) — the only file you edit to change scoring: a `policy_version` plus a `metrics:` map of `{weight, normalize}` per metric name. `normalize` is one of `minmax` / `zscore` / `linear` / `none` (`linear` and `none` are currently the same pass-through — kept as separate labels for documentation intent).
9. **`lib/score.py`** — loads `policy.yaml`, syncs it into `policy_weights` (replacing any existing rows for that `policy_version`), then for a given date normalizes each metric's values **across that date's slate only** (not the whole season) before applying weights, and writes one summed `total_score` row per `(game_id, team_id)` to `daily_scores`. The actual scoring math (normalize + weight + sum) lives in `compute_scores()`, split out from `compute_daily_scores()` specifically so `lib/policy_backtest.py` can reuse the identical logic to replay historical dates under a different policy's weights without persisting anything — `compute_daily_scores()` is just `compute_scores()` plus the delete/insert into `daily_scores`. Missing metric values (e.g. a team's first game of the season has no `rest_days`, or no completed games yet for `recent_form`) simply don't contribute to the sum rather than erroring. `score.py` only ever deletes/replaces rows for the exact `policy_version` it's currently writing — it never touches a different version's rows for the same date — so a date that gets (re-)scored both before and after a `policy.yaml` weight change ends up with rows from *two* `policy_version`s in `daily_scores` simultaneously (this happens whenever `run_daily.py` runs for "today" again after `policy.yaml` changes mid-day, and it already happened at least once before this was noticed — see the `build_picks()`/`policy_performance()` fix below). Nothing deletes the stale version's rows for that date; readers have to know to pick one.
10. **`lib/report.py`** — `build_picks()` reads a date's `daily_scores` only under one `policy_version`: `SELECT MAX(policy_version) FROM daily_scores WHERE date = ?`, lexicographically latest among whatever's actually on record for that date (not necessarily whatever's current in `policy.yaml` right now — a past date normally only has one version on record regardless, so this doesn't require re-scoring history every time `policy.yaml` changes). Before this filter existed, a date carrying rows from two `policy_version`s (see `score.py` above) would pick whichever row SQLite happened to return last for a given `(game, team)` — undefined in practice, not a real decision — which is exactly what was happening the first time this was actually tested with two versions scoring the same day. For each game, whichever team's `daily_scores.total_score` is higher under that one chosen version is "the pick"; every scored game is ranked by the score gap between the two teams (not by raw score, and not cut to a top-N), printed as a table, written to CSV + HTML (see above), and logged into `picks_log` (spread/moneyline pulled from `odds` via `_dk_or_consensus()`: DraftKings' own latest quote — `PRIMARY_BOOK` — if it has one, else a cross-book average of each bookmaker's latest quote). The cross-book average only ever kicks in on a game DraftKings hasn't posted a line for yet; it can otherwise produce a line no real book would offer when bookmakers disagree on the favorite (e.g. some books at -1.5, others at +1.5 for the same team, averaging to something like -0.17) — using DraftKings directly avoids that. The HTML table is laid out like a sportsbook board (matching the actual DraftKings app): two rows per game, away team on top and home team below, full borders on every cell with generous padding so each game reads as a distinct grid block, with **Puck Line / Over-Under / Money Line** columns for each team's side of those three markets — the per-game columns (Edge, Score, ML Result, Vs. Puck Line, Team ATS Record, Notes) span both rows via `rowspan`, and both rows share one alternating background per *game* (`tr.game-even`/`tr.game-odd` CSS classes) rather than per physical row, since plain `nth-child` striping would just color every home row. Note it's `tr.game-even`/`tr.game-odd`, not the bare `.game-even`/`.game-odd` this first shipped with — a bare class selector is *less specific* than the pre-existing `tr:nth-child(even) td` rule (both are shared across every page via `HTML_STYLE`) and silently lost to it, so the original per-game highlighting never actually took effect until the `tr` was added to match that rule's specificity exactly and win on source order. Every price shown (puck line, total, moneyline) is followed by its devigged implied probability in parens via the shared `devig_pair()` helper — same math as `market_edge`, purely for display, not stored anywhere. The puck-line price itself (e.g. the `+180` next to a `-1.5` line) comes from `odds.home_spread_price`/`away_spread_price`, which `fetch_odds.py` only started capturing once this was built — The Odds API's `spreads` market always included a price per side, it just wasn't being read before. `ML Result` is colored the same way as `Vs. Puck Line` (green win / red loss, via `format_outcome_colored()`); the `Score` cell also shows whether the actual combined score went Over/Under/Push against `total` in parens (e.g. "4–8 (Over)"), comparing against whatever total was last on record for that game — since odds stop updating once a game goes final, this is naturally stable without any special-casing. Every generated page's "Last updated" footer (`generation_timestamp()`) is US Eastern via `zoneinfo`, not UTC — it reads as EDT or EST automatically depending on whether daylight saving is in effect when it runs, rather than a hardcoded label. Re-running for a date replaces that date's *ungraded* `picks_log` rows only, so grading results already recorded aren't clobbered.

The page header only shows the date (`<p class="subtitle">{pretty_date}</p>`) plus the Est. Winnings dropdown on today's page — the long explanation of how to read the table (what each column means, that the three "pick" columns are independent recommendations, etc.) is a `<p class="legend">` moved below the table instead, right before the disclaimer/timestamp footer. It used to all be one `<p class="subtitle">` block above the table; moved so the page gets straight to the controls and the table itself before the reader has to scroll past several sentences of explanation, while keeping that explanation available (just at the bottom) for anyone who wants it.

`HTML_STYLE` (shared by every page type — picks reports, `policy.html`, `record.html`, `index.html`) sizes the page at `max-width: 1400px` rather than the original 760px, specifically so the 12-column picks table fits on a typical desktop browser without horizontal scrolling — 760px was fine for the simpler early reports but far too narrow once the table grew this wide. `.table-scroll`'s `overflow-x: auto` wrapper (the horizontal-scroll fallback for anything narrower, e.g. a phone) is now scoped off via `@media (min-width: 1400px) { .table-scroll { overflow-x: visible; } }` rather than left always-on, for a reason that isn't just cosmetic: leaving `overflow-x: auto` always active would silently break the sticky table header below it. Setting `overflow-x` to anything but `visible` makes browsers implicitly upgrade the paired, un-set `overflow-y` to `auto` too (per the CSS Overflow spec's rule for mismatched visible/non-visible pairs), which turns that div into its own scroll container — and `position: sticky` sticks to the *nearest* scroll container, not necessarily the page. Inside an always-auto wrapper, `thead th { position: sticky; top: 0; }` would stick to the wrapper's own box (which never independently scrolls, since it isn't height-constrained) instead of the viewport, so the header would silently fail to freeze while scrolling the actual page — the exact kind of silent CSS failure the `tr.game-even`/`tr.game-odd` specificity bug above was. Scoping the scroll wrapper to narrow viewports only keeps it structurally `overflow-x: visible` (a true no-op, not a scroll container) everywhere the horizontal scroll isn't actually needed, which is what lets the sticky header actually freeze on desktop.

Each game's two `<tr>`s also carry a `row-away`/`row-home` class (alongside the existing `game-even`/`game-odd` parity class) for two purely visual reasons, neither of which changes any pick logic: `tr.row-away td { border-top: 2px ...}`/`tr.row-home td { border-bottom: 2px ...}` thickens just the top edge of a game's first row and the bottom edge of its second, framing each game's own pair of rows as one block while the border *between* the away and home row of the same game stays the default 1px (collapsed borders resolve conflicting widths by picking the wider one, so this also reinforces the shared edge with the next game). The home team's own name cell additionally gets a `home-cell` class with a light `color-mix(in srgb, var(--accent) 14%, var(--bg))` tint, so which team is home is visible without reading the row order — same specificity gotcha as the `tr.game-even`/`tr.game-odd` rules above: a bare `.home-cell` (0,1,1) would lose to `tr.game-even td` (0,1,2), so it's qualified as `tr.row-home td.home-cell` (0,2,2) to win outright regardless of source order. This background and the `.pick` class's green text color are orthogonal CSS properties on the same cell, so a home team that's also the Money Line pick correctly shows both at once.

The green `<strong class="pick">` highlight is applied independently in each of the three market columns, not just once per game — each column has its own recommendation, computed differently, and they can (and routinely do) disagree:
- **Money Line**: the same overall pick driven by `daily_scores.total_score` (policy.yaml's weighted score) — unchanged from before.
- **Puck Line**: `puck_line_recommendation()` projects this game's scoring margin as the home and away teams' own recent `goal_differential` (from `form_metrics.py`) against each other, with no further weighting, and checks whether that projected margin clears the fixed 1.5-goal line in the favorite's direction — recommending the underdog (+1.5) instead of the favorite (-1.5) when it doesn't. This is a genuinely separate read from Money Line (a team can be the better overall team — and thus the Money Line pick — while still projecting to win by less than 1.5, which recommends betting *against* them on the puck line).
- **Over/Under**: `total_recommendation()` projects the game's combined total as each team's expected goals (the average of its own `goals_for_avg` and the opponent's `goals_against_avg`, both from `form_metrics.py`), summed, and compares that to the market's own total line.
Both are intentionally simple, un-weighted projections (not policy.yaml metrics) — they're answering "does this number clear a fixed market line," a different kind of question than Money Line's "which team scores higher," so they don't belong in the same weighted-sum machinery. Either returns `None` (no highlight on either side) when there isn't enough trailing-game data yet (e.g. a team's first few games of the season) or the projection lands exactly on the market's line.

Only when `target_date` is actually today (`is_today` inside `render_html_report()`), the page also gets an **Est. Winnings** column and a Money Line/Puck Line/Over-Under dropdown above the table — the one piece of client-side JavaScript on the whole site (everything else is pure static HTML). The dropdown does two things at once, both driven by the same `onMarketChange()` handler: each pick's rowspan'd winnings cell carries `data-ml`/`data-pl`/`data-ou` attributes (the moneyline, puck-line, and over/under prices, via `pick_spread_price`/`total_price_at_pick` in `build_picks()`), pre-rendered server-side for the default (Money Line) selection via `potential_payout()` — a pure "profit on a $`STAKE` bet if it wins" function, deliberately not `grade.py`'s `odds_profit()`, which needs a known win/loss outcome that an ungraded pick doesn't have yet — and switching it also filters the table down to just that market's two columns (Puck Line/Over-Under/Money Line each tagged `col-pl`/`col-ou`/`col-ml` via `market_col_attrs()`, toggled by `updateColumns()`; everything else — Edge, Score, Team ATS Record, etc. — always stays visible, since those aren't "pick" columns). The default view (Money Line selected) is pre-rendered server-side with the other two columns' cells already `style="display:none"`, the same way the default winnings figure is pre-rendered — not left for JS to apply on load — so there's no flash of all three columns before the script runs. Past-date pages still get the `col-*` classes on their cells (harmless, since `build_picks()`/`render_game_rows()` don't branch on `is_today` for that part) but never get the dropdown, the JS, or the `style="display:none"` default, so every column stays visible there exactly as before. Switching the dropdown runs inline `updateWinnings()`/`updateColumns()`, which re-read `data-*`/`class` attributes already in the page and recompute — no network round-trip, since this is a fully static page. The whole dropdown is gated to today only because Est. Winnings is inherently forward-looking ("if this pick wins, here's the payout") — past dates are already graded, so their real win/loss and actual `profit_10` (on `record.html`/`backtest.py`) is what matters there, not a hypothetical.

Below the table, an **"If You Bet Every Pick"** table (`day_totals_html` inside `render_html_report()`) shows that day's actual $ outcome, per bet type, if every one of that type's recommendations on the slate had been bet at a flat $`STAKE` — one row each for Money Line, Puck Line, and Over/Under, built from the `profit_10`/`puck_line_profit_10`/`total_profit_10` columns `build_picks()` now pulls from `picks_log` alongside `result`/`straight_up_result`. `format_day_total()` distinguishes three states, not just "has a number or doesn't": **not yet graded** (none of the day's games are final yet), **no odds on record** (the games are final, but no price was ever captured for that bet type — e.g. dates before `fetch_odds.py` started saving `home_spread_price`/`away_spread_price`, so there's a real win/loss but no price to compute a dollar figure from), and **no recommendation today** (no game had a Puck Line/Over-Under recommendation to begin with, e.g. not enough trailing-game data). Collapsing these into one generic "no total yet" message would misreport an already-decided day as still pending, so they're kept distinct.

A fourth row, **Strategy**, and a matching **Strategy** column in the main table (both on every page, not gated to today) surface a simple, data-driven betting rule derived from analyzing the first few weeks of graded picks (not a formula anywhere else in this codebase — see `strategy_markets()` in `report.py`): always bet Puck Line when it has a recommendation, and only bet Money Line too on games where it agrees with the Puck Line pick — Over/Under is never recommended, since it was a net loser across the sample it was derived from. `strategy_markets(pick_team, puck_line_pick)` returns which markets apply to a game (`["pl", "ml"]`, `["pl"]`, or `[]` with no Puck Line recommendation at all); the table column shows the recommended team and which market(s), and the day-total row sums whichever legs actually apply per game (one bet on a disagreement game, two on an agreement game) using the same three-state not-yet-graded/no-odds/no-recommendation logic as the other rows. This is explicitly a small-sample read (barely 20 graded games when it was derived) surfaced in the UI as a live, ongoing hypothesis, not a finished model — expect `strategy_markets()`'s rule to get revised as more games are graded and `policy_backtest.py`/manual analysis says otherwise.
11. **`lib/policy_page.py`** — renders `docs/reports/policies/policy.html` straight from `policy.yaml` plus the `metrics` catalog; a read-only reference, not a data output.
12. **`lib/grade.py`** — grades every `picks_log` row whose game is final (`game_state = 'OFF'`, both scores present) and still missing a result, for all three independent bet types (Money Line, Puck Line, Over/Under — see `report.py`'s entry below): `result`/`straight_up_result`/`profit_10` for Money Line (`result` grades the Money Line pick against the spread in `spread_at_pick`; `straight_up_result` is whether the picked team won outright; `profit_10` is the $ profit/loss a flat $`STAKE` (currently $10) moneyline bet at `moneyline_at_pick` would have made, settled on `straight_up_result` since moneyline bets pay on who wins, not who covers); `puck_line_result`/`puck_line_profit_10` the same way but against whichever team `puck_line_pick` named (which can differ from the Money Line pick) and its own `puck_line_spread_at_pick`/`puck_line_price_at_pick`; `total_result`/`total_profit_10` against `total_at_pick`/`total_price_at_pick` and whatever `total_pick` ('Over'/'Under') was recommended. These price-time fields are often `NULL` (no odds fetched that day, or — for Puck Line specifically — dates before `fetch_odds.py` started capturing `home_spread_price`/`away_spread_price` at all) — a row can still get a win/loss result from the final score even with no price to compute a dollar figure from, same as `straight_up_result` already worked without `moneyline_at_pick`. The shared `odds_profit(price, result)` helper computes P&L for all three bet types (win/loss/push), used in place of the old moneyline-only `moneyline_profit()`. Safe to re-run; only touches rows still missing any gradeable result. `STAKE` lives in `grade.py` and is imported by `backtest.py`/`record_page.py`/`report.py` rather than redeclared, so changing the bet size is a one-line edit in one place.
13. **`lib/record_page.py`** — renders `docs/reports/record.html`: picks_log's overall record and ROI for all three bet types (Money Line, Puck Line, Over/Under — each as its own row, via `backtest.py`'s `bet_type_totals()`/`policy_performance()` rather than re-deriving them), plus a per-`policy_version` Money Line breakdown (Puck Line/Over-Under aren't policy.yaml-driven, so a per-version breakdown of those wouldn't mean anything — they get one overall total each instead), plus a third **Policy Backtest** table from `policy_backtest.py`'s `build_policy_backtest()`/`rank_by_roi()` replaying every policy_version against the exact same full slate of completed games (a fair comparison, unlike the "By Policy Version" table above it). The published, no-terminal counterpart to `backtest.py`/`policy_backtest.py`'s console output — linked from `docs/index.html` as "Performance record & ROI," guarded the same way as the "Today's Picks" link so a fresh deploy never shows a dead link before the page exists once. `run_daily.py` already called `build_record_page()` right after grading before this; wiring the policy backtest into that same function means it gets refreshed on every run too, with no `run_daily.py` changes needed — exactly the "update this every time we grade games" ask that prompted adding it here instead of leaving it a manual, terminal-only check.

**Bankroll Over Time**: a day-by-day cumulative-P&L line chart (`render_bankroll_chart()`), one line each for Money Line, Puck Line, Over/Under, and the Strategy combo (same `strategy_markets()` logic `report.py`'s day-total uses, just cumulative across every date instead of one day — `bankroll_series()` sums each date's legs into a running total per track, skipping a date entirely if nothing on it is graded yet rather than plotting it as a flat/misleading segment). Rendered as plain inline `<svg>` with hand-computed `<polyline>` coordinates — no JS, no charting library, no CDN, matching the site's fully-static design; colors come from four new `--chart-*` CSS variables in `HTML_STYLE` (light/dark aware, same pattern as every other color on the site) rather than hardcoded hex in the SVG markup, so the chart themes correctly too. Below the chart, a small table adds **Current Streak** (the most recent run of consecutive Money Line wins or losses, scanned backward from the latest graded pick) and **Best/Worst Single Pick** (the single graded pick with the highest/lowest `profit_10`, by date and team) — both computed directly from `picks_log`, no new tables. Verified the chart's final cumulative values against a raw `SUM(profit_10)` query and an independent manual recomputation of the Strategy track before publishing; both matched exactly.
14. **`bin/run_daily.py`** — orchestrates steps 2–13 for one date by inserting `lib/` onto `sys.path` and importing/calling each module's entrypoint function directly (no subprocesses). Since every stage is either an upsert or a full rebuild, there's no "only run what's needed" logic — it just runs everything every time, which is simpler and still cheap. Its schedule fetch uses a `--lookback-days` window (default 3) behind the target date so recently-completed games' final scores get upserted even after they've aged out of being "today," and grading runs right after that fetch so those newly-final scores get graded the same run. `record_page.py` is rebuilt immediately after grading (so it's always current before the "refresh every past report" loop checks whether to link it), and `market_metrics.py` runs even when `ODDS_API_KEY` isn't set, rebuilding from whatever odds snapshots are already on record. As its very last step, `push_to_github()` commits and pushes any changed files under `docs/` to `origin/main` — scoped to `docs/` specifically (not `git add -A`) so it never sweeps in unrelated, in-progress source edits sitting uncommitted elsewhere in the repo; it first checks `git status --porcelain -- docs` and does nothing if that's empty, rather than attempting (and failing) an empty commit. A git failure here (no network, a stale local git identity, a push conflict) is caught and printed as a warning, not raised — the pipeline's real work (the local database and generated reports) already succeeded regardless of whether publishing them does, so a publish failure shouldn't read as a pipeline failure. Pass `--no-push` to skip this step entirely, e.g. while testing a change locally before it's ready to publish — every manual run throughout this project's development has otherwise used `run_daily.py` directly, so an unconditional auto-push would have pushed every test run straight to the public site.
15. **`bin/run_daily_cron.sh`** — cron-safe wrapper around `run_daily.py` for unattended daily runs (absolute paths, sources `.env`, logs to `nhl_toolkit/logs/`).

`lib/arenas.py` is static reference data (lat/lon + IANA timezone per team, keyed by the 3-letter abbrev the NHL API uses), plus `TEAM_NAME_TO_ABBREV`, a reverse lookup built from that same data for feeds (like odds) that identify teams by full name. Note the ARI→UTA relocation: `ARENAS["ARI"]` is aliased to the same record as `ARENAS["UTA"]` so historical pre-2024-25 data still resolves. `ARENAS["UTA"]["team"]` is the current "Utah Mammoth" (their permanent name as of the 2025-26 season) with "Utah Hockey Club" (their 2024-25 inaugural-season placeholder name) kept as an extra `TEAM_NAME_TO_ABBREV` alias. `ARENAS["MTL"]["team"]` is "Montréal Canadiens" *with the accent* — that's the exact spelling The Odds API uses, with the unaccented "Montreal Canadiens" kept as a fallback alias. Both of these are the same failure mode: an exact-match name lookup silently dropped every odds quote for that franchise's entire history (Utah: a stale pre-rename name; Montreal: a missing diacritic) until each was caught by querying The Odds API directly and diffing its `home_team`/`away_team` strings against what was hardcoded here. If a team's odds are mysteriously always missing, suspect this exact failure mode first and verify against the live feed rather than guessing — don't assume `TEAM_NAME_TO_ABBREV`'s spelling is right just because it looks plausible.

`lib/backtest.py` is a standalone, read-only diagnostic (`python lib/backtest.py`, not wired into `run_daily.py`) for tuning `policy.yaml` weights: it correlates each metric's home-minus-away differential against the actual final goal margin across every completed game, and prints `picks_log`'s real straight-up/ATS record *and* moneyline ROI (summed `profit_10` on a flat $10 stake per pick, as a % of total staked) per `policy_version`, plus (via `bet_type_totals()`) the same record+ROI for the Puck Line and Over/Under recommendations as one overall total each, independent of `policy_version` since neither is policy.yaml-driven. `policy_performance()`'s join to `daily_scores` goes through a subquery that, same as `build_picks()`, picks one `policy_version` per date (lexicographically latest among whatever's on record for that date) rather than joining to every version a date happens to carry — a plain join would double-count a pick under every `policy_version` that ever scored its date, inflating whichever version a date's rows got left behind under after a later re-score. This was caught by direct comparison: before the fix, `2026-08-v2`'s reported record included games from a date that had since been re-scored under `2026-10-v1`, inflating it from its real 2-1 (+34.4% ROI, 3 bets) to a phantom 8-3 (+30.7%, 11 bets) that never actually happened under that version alone. It never hardcodes a metric name — it reads whatever rows exist in the `metrics` table, so a future metric (injuries, head-to-head, goalie quality) shows up here automatically the first time something populates its `metric_values`, with zero changes to this file (this is exactly how `market_edge`'s correlation went from `n/a` under the old spread-based computation to a real, non-zero value once it was reworked onto the moneyline — no `backtest.py` changes needed either time). It's purely advisory (never writes to `policy.yaml`); a metric's correlation sign/magnitude is a hint for hand-tuning its weight, not a verdict, especially early in a season when sample sizes are tiny (see `--min-n`). Note `home_ice` always correlates as `n/a`: its home-minus-away differential is definitionally constant (1 for every game), so this particular diagnostic can't say anything about it.

`lib/policy_backtest.py` is a second, complementary standalone diagnostic that answers a different question than `backtest.py`'s live `policy_performance()`: not "how did each policy actually do during the stretch it happened to be live for" (different, non-overlapping date ranges per version, so not a fair comparison — a version that happened to be live during a lucky week looks artificially strong), but "how would every policy_version ever synced into `policy_weights` have performed if it had scored *every* completed game this season." It replays each date's slate under each policy's weights via `score.py`'s `compute_scores()` (extracted from `compute_daily_scores()` specifically so this reuses the exact real scoring math instead of a parallel reimplementation that could drift from it), determines the simulated Money Line pick, and grades it against the actual final score plus whatever odds are on record (via `report.py`'s `latest_consensus_spread()`/`latest_consensus_moneyline()` and `grade.py`'s `odds_profit()`) — entirely in memory, never writing to `daily_scores`/`picks_log`, which represent what was actually live and bet on, not a simulation. Scales to new policies automatically: every `policy_version` ever synced into `policy_weights` (any time `score.py` runs after a `policy.yaml` change) is included the next time this runs, with no registration step. First real run already demonstrated exactly why this exists: `2026-08-v2`'s *live* record looked best (72.7% SU, +30.7% ROI, but only ever judged on 3 games from one lucky date), while replayed fairly across the same 21 completed games every other version was judged on, it's clearly the worst (42.9% SU, -19.1% ROI). It's also a lesson in how thin the sample still is either way: a week later, with 34 games instead of 21, the ranking between `2026-10-v1` and `2026-10-v2` flipped (`v1` pulled ahead, `v2` went net-negative) — worth re-running regularly rather than trusting any single snapshot, which is exactly why `record_page.py` now publishes this on every run rather than leaving it a manual, point-in-time check. `print_policy_backtest()`'s ranking logic is split out into `rank_by_roi()` (and `roi_pct()`) specifically so `record_page.py` can reuse the identical ranking instead of re-deriving it.

SQLite was chosen deliberately for zero-config local development; the schema is kept plain enough that a future Postgres migration is meant to be a straight port, not a rewrite (see `lib/db.py` docstring).

## Roadmap (not yet implemented)

Per `nhl_toolkit/README.md` and `betting-toolkit-design.md`:

- An `injuries` table (deferred as the messiest data source — likely needs scraping) and injury-derived metrics.
- Head-to-head record and starting-goalie quality — the generic `metrics`/`metric_values` schema already supports adding these without touching `score.py` or `lib/backtest.py`, but nothing populates them yet. (`recent_form`/`goal_differential` are now implemented, in `form_metrics.py`.)

The cumulative-edge/streaks view (running bankroll chart, current streak, best/worst single pick) that used to be listed here is done — see `lib/record_page.py`'s Bankroll Over Time section in Architecture below.

Further out, not yet designed — see `betting-toolkit-design.md` section 10: player-level stats sourced from MoneyPuck.com (especially goalie data), which would need a schema step up from today's team-level-only tables; and eventually tracking/placing real bets, a materially different feature from the current paper-trading `picks_log`/grading design.

Don't assume any of this exists — check the actual code before referencing it.
