# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

The repository root has no top-level app yet (just this file and a placeholder `README.md`). The only real code lives in `nhl_toolkit/`, a Python toolkit now spanning Phase 1 (schedule ingestion + travel/rest metrics) and Phase 2 (odds ingestion, the generic policy-driven scoring engine, and the daily full-slate picks report). There is no test suite yet — dependencies are managed by hand (`pip install requests pyyaml`; everything else is stdlib).

Use a repo-root `.venv` (not a per-subdirectory one) even though `nhl_toolkit/` is the only Python code today — see `.gitignore` (`.venv/`, `*.db`, `.env`, and `nhl_toolkit/reports/` are excluded from version control).

`betting-toolkit-design.md` (repo root) is the full project design doc — read it before planning any new work here. It lays out the end goal: a scheduled, no-LLM Python pipeline that fetches NHL schedule/odds/injury/travel data into a database, scores every game through a config-driven weighted policy engine (`policy.yaml`), outputs a daily picks report ranking every game by edge, and logs outcomes for backtesting. `nhl_toolkit/` now covers build-order steps 1–7 of that design (arenas, schedule ingestion, travel/rest metrics, odds ingestion, the policy engine, the daily report/`picks_log`, and grading) — only the `injuries` table and the ROI/weight-tuning analysis remain design-only.

Odds ingestion requires a free API key from https://the-odds-api.com, stored as `export ODDS_API_KEY=...` in a repo-root `.env` (gitignored, never commit it) and loaded with `source .env` before running `lib/fetch_odds.py`.

## Commands

Run all commands from `nhl_toolkit/`. Entry-point scripts you run directly live in `bin/`; everything they import lives in `lib/`.

```bash
pip install requests pyyaml                                # third-party dependencies

source .env && python bin/run_daily.py --date 2026-10-01   # run the full pipeline for one date and build its report
```

`bin/run_daily.py` is the normal way to produce a day's report: it runs every step below in order (fetching just that date's game-week, so it's cheap even run daily) and skips the odds step gracefully if `ODDS_API_KEY` isn't set. Each stage can also be run standalone:

```bash
python lib/db.py                                           # create nhl.db + schema (also runs automatically from every script below)
python lib/fetch_schedule.py --start 2026-10-01 --end 2026-10-31   # upsert schedule/scores for a date range (defaults to today's game week)
python lib/grade.py                                         # grade any newly-final picks_log rows (result + straight_up_result)
python lib/travel_metrics.py                               # rebuild schedule_context (rest/travel/timezone metrics) from `games`
python lib/metrics.py                                      # bridge schedule_context into the generic metrics/metric_values schema
python lib/form_metrics.py                                 # rebuild recent_form/goal_differential metric_values from `games` scores
source .env && python lib/fetch_odds.py                    # append an odds snapshot per (game, bookmaker) from The Odds API
python lib/market_metrics.py                                # derive market_edge metric_values from odds on record
python lib/score.py --date 2026-10-01                       # apply policy.yaml to metric_values -> daily_scores
python lib/report.py --date 2026-10-01                      # rank every game by score gap, print/write CSV + HTML, log to picks_log
python lib/backtest.py                                      # not part of run_daily.py -- a manual tuning aid, see below
```

`fetch_schedule.py` is an upsert and safe to re-run daily to pick up final scores. `travel_metrics.py`, `metrics.py`, and `form_metrics.py` fully delete-and-rebuild the metric_values rows they own each run — always re-run them in order (`travel_metrics.py` then `metrics.py`/`form_metrics.py`, either order between those two) after `fetch_schedule.py`, since none of them rebuild automatically (`run_daily.py` handles this ordering for you). `fetch_odds.py` only appends (never deletes), so re-running it accumulates a quote history rather than duplicating in an upsert sense. `market_metrics.py` fully delete-and-rebuilds like `travel_metrics.py`/`metrics.py`/`form_metrics.py` do, but always from whatever's currently in `odds` regardless of whether `fetch_odds.py` ran this time — run it after `fetch_odds.py` and before `score.py`. `score.py` and `report.py` are each idempotent per `(date, policy_version)` — rerunning replaces that date's rows rather than duplicating them. `grade.py` only touches `picks_log` rows that are still ungraded (`result IS NULL OR straight_up_result IS NULL`), so it's safe to re-run as often as you like and never re-grades or overwrites an already-graded row. (All of these live under `lib/`.)

`report.py` writes three outputs: a local CSV (`nhl_toolkit/reports/`, gitignored), a static HTML page (`docs/reports/picks/picks_{date}.html`, git-tracked), and a regenerated `docs/index.html` linking every report newest-first. If `target_date` is actually today, it also writes `docs/reports/picks/current.html` — a byte-identical copy at a stable filename, so a bookmarked/shared URL always shows the latest picks without the date in it. (A real symlink would be more "correct" but doesn't survive a GitHub Pages build, which runs in Jekyll's safe mode and ignores symlinked files; a duplicated file is the static-hosting-safe equivalent.) `current.html` is only ever written when rendering *today's* actual report — the full-history refresh loop in `run_daily.py` re-renders every past date too, and must never clobber it with stale content. `docs/index.html` links to it as "Today's Picks" whenever it exists. The `docs/` folder is meant to be served via GitHub Pages (repo root or `/docs` on `main`) and is now live at https://babruzi.github.io/hockey-web/ (repo was made public to enable free-tier Pages).

`policy_page.py` renders `docs/reports/policies/policy.html`, a reference table of every metric in `policy.yaml` (weight, normalize method, description/unit from the `metrics` catalog) — linked from the reports index, meant to make weight-tuning easier without opening the YAML. It reads `policy.yaml` directly each time, so it's always current; nothing needs to be kept in sync by hand. `run_daily.py` regenerates it every run. `docs/reports/` has two subdirectories: `picks/` (one HTML page per scored date) and `policies/` (currently just the one current-policy reference page — a natural place for a per-`policy_version` history later, but nothing writes one yet).

### Running this daily / accumulating a season's data

`nhl.db` is meant to be a long-lived, ever-growing local database, not something reset between runs — nothing in this pipeline drops or replaces the whole DB (`*.db` is gitignored deliberately; GitHub is for code backup only, not data). One-time backfill for a season already in progress, then run daily from there:

```bash
python lib/fetch_schedule.py --start 2026-10-01 --end 2026-10-31   # backfill however far the season has gotten
python bin/run_daily.py --date 2026-10-01                           # then run_daily.py daily going forward
```

`run_daily.py` re-fetches a trailing `--lookback-days` window (default 3) behind `--date` in addition to that date's game-week, so games that finished in the last few days get their final score upserted even after they're no longer "today" — without this, a game played yesterday would stay stuck at its pre-game state forever once `--date` moves past it. If you ever miss several days of runs, re-run the backfill command above to close the gap (upserts are idempotent, so overlapping ranges are harmless).

For unattended daily runs, `run_daily_cron.sh` is a cron-safe wrapper (absolute paths, sources `.env`, logs to `nhl_toolkit/logs/`, both gitignored):

```
0 9 * * * /Users/babruzi/Documents/VSCODE/GITHUB/hockey-web/nhl_toolkit/bin/run_daily_cron.sh
```

## Architecture

Data flows through a pipeline of scripts, each its own file under `nhl_toolkit/lib/`, all sharing one SQLite DB (`nhl_toolkit/nhl.db`). `nhl_toolkit/bin/` holds the two scripts meant to be invoked directly (`run_daily.py` and its cron wrapper); everything else is a `lib/` module that either gets imported by `run_daily.py` or run standalone for one pipeline stage.

**Phase 1 — schedule and travel:**
1. **`lib/db.py`** — owns the schema (all tables below). `games` is raw schedule/score data keyed by the NHL's own `game_id`. `schedule_context` is one row per `(game_id, team_id)` holding derived metrics (rest days, games in trailing 7/14/30 days, distance traveled, timezones crossed, back-to-back flag), FK'd to `games`.
2. **`lib/fetch_schedule.py`** — pulls from the NHL Web API (`api-web.nhle.com/v1/schedule/{date}`), which returns a ~7-day "game week" per call. Walks a date range one game-week at a time and upserts into `games` (`ON CONFLICT(game_id) DO UPDATE` on score/state/start-time — never inserts duplicates).
3. **`lib/travel_metrics.py`** — reads `games` per-team in chronological order and derives `schedule_context` by walking each team's game history once, carrying rolling state (previous venue, previous date, trailing played-dates window). Distance and timezone-shift math depends on `lib/arenas.py`.

**Phase 2 — odds, generic metrics, and policy-driven scoring:**
4. **`lib/metrics.py`** — bridges `schedule_context`'s fixed columns into the design doc's generic `metrics`/`metric_values` tables (one row per name in `metrics`, one row per `(game_id, team_id, metric_id)` in `metric_values`). This is what lets new scoring factors (injuries, recent form, odds movement) get added later as data instead of schema/code changes.
5. **`lib/form_metrics.py`** — derives four metrics straight from `games` (no separate context table needed): `recent_form` (win % over a team's last 10 completed games), `goal_differential` (average goal margin over that window), and `goals_for_avg`/`goals_against_avg` (average goals scored/allowed over the same window — added later to drive `report.py`'s Over/Under recommendation; `goal_differential` is exactly `goals_for_avg - goals_against_avg`, computed from the same rolling deques). Walks each team's full game history chronologically, but only updates its rolling window on completed games — **the NHL Web API marks a completed game's `game_state` as `"OFF"`, not `"FINAL"`** (the `games.game_state` column comment used to claim otherwise; that was wrong and silently broke this until it was caught by checking against a real, already-completed season's scores). A metric_values row is written for every game including future ones, using only games already played, so there's no lookahead into the game being scored. `goals_for_avg`/`goals_against_avg` are never added to `policy.yaml` — `score.py` only applies weights for metric names explicitly listed there, so seeding a new metric into the `metrics` table never silently changes `total_score`/the Money Line pick unless you also weight it.
6. **`lib/fetch_odds.py`** — pulls moneyline/puck-line/totals from The Odds API (`icehockey_nhl` sport key) and appends snapshot rows to `odds`, one per `(game, bookmaker)` per run — it's an append-only time series, not an upsert, so re-running frequently is how line-movement gets tracked later. Captures a price for every market including `spreads` (`home_spread_price`/`away_spread_price`) — the feed always included this, it just wasn't read into the schema until `report.py` needed it for the puck-line's own price, not only the home/away moneylines. Since the feed identifies teams by full name, not abbrev, matching a quote to a `games` row goes through `arenas.TEAM_NAME_TO_ABBREV` and then a `(home_abbrev, away_abbrev, local_game_date)` lookup — the local date is computed by converting the feed's UTC `commence_time` into the home arena's timezone.
7. **`lib/market_metrics.py`** — derives a `market_edge` metric from `odds`: each team's devigged, market-implied win probability, computed from the moneyline (not the puck-line spread — NHL puck lines are fixed at 1.5 goals in every quote this pipeline has ever recorded, so a spread-based version of this metric is nearly a constant and carries almost no signal; the moneyline is where the market's actual opinion about *how much* it favors a team lives, e.g. a -218/+180 line vs. a -115/-105 line on an identical ±1.5 spread). Devigging means converting both sides' American odds to raw implied probabilities and dividing each by their sum, removing the bookmaker's overround so the two sides sum to exactly 1. Uses DraftKings' own moneyline (`PRIMARY_BOOK`, kept in sync with `report.py`'s copy of the same constant by hand to avoid a circular import) when it has posted one, falling back to a cross-book average of every bookmaker's devigged probability otherwise. This is what actually puts the betting market into the weighted scoring equation — previously `spread_at_pick` only fed `report.py`'s display and `grade.py`'s after-the-fact ATS grading, never `score.py`'s `total_score`. Fulfills the "market line movement (steam)" metric from `betting-toolkit-design.md`'s original starter catalog (section 5), left unimplemented until now. Like `recent_form`/`goal_differential`, a `(game, team)` pair with no odds quote simply gets no value rather than erroring. Needed no changes to `score.py`, `report.py`, or `backtest.py` — adding (and later reworking) it was purely a matter of writing to `metric_values` and adding a line to `policy.yaml`, which is exactly the point of the generic metrics schema.
8. **`policy.yaml`** (repo: `nhl_toolkit/policy.yaml`) — the only file you edit to change scoring: a `policy_version` plus a `metrics:` map of `{weight, normalize}` per metric name. `normalize` is one of `minmax` / `zscore` / `linear` / `none` (`linear` and `none` are currently the same pass-through — kept as separate labels for documentation intent).
9. **`lib/score.py`** — loads `policy.yaml`, syncs it into `policy_weights` (replacing any existing rows for that `policy_version`), then for a given date normalizes each metric's values **across that date's slate only** (not the whole season) before applying weights, and writes one summed `total_score` row per `(game_id, team_id)` to `daily_scores`. Missing metric values (e.g. a team's first game of the season has no `rest_days`, or no completed games yet for `recent_form`) simply don't contribute to the sum rather than erroring.
10. **`lib/report.py`** — for each game, whichever team's `daily_scores.total_score` is higher is "the pick"; every scored game is ranked by the score gap between the two teams (not by raw score, and not cut to a top-N), printed as a table, written to CSV + HTML (see above), and logged into `picks_log` (spread/moneyline pulled from `odds` via `_dk_or_consensus()`: DraftKings' own latest quote — `PRIMARY_BOOK` — if it has one, else a cross-book average of each bookmaker's latest quote). The cross-book average only ever kicks in on a game DraftKings hasn't posted a line for yet; it can otherwise produce a line no real book would offer when bookmakers disagree on the favorite (e.g. some books at -1.5, others at +1.5 for the same team, averaging to something like -0.17) — using DraftKings directly avoids that. The HTML table is laid out like a sportsbook board (matching the actual DraftKings app): two rows per game, away team on top and home team below, full borders on every cell with generous padding so each game reads as a distinct grid block, with **Puck Line / Over-Under / Money Line** columns for each team's side of those three markets — the per-game columns (Edge, Score, ML Result, Vs. Puck Line, Team ATS Record, Notes) span both rows via `rowspan`, and both rows share one alternating background per *game* (`tr.game-even`/`tr.game-odd` CSS classes) rather than per physical row, since plain `nth-child` striping would just color every home row. Note it's `tr.game-even`/`tr.game-odd`, not the bare `.game-even`/`.game-odd` this first shipped with — a bare class selector is *less specific* than the pre-existing `tr:nth-child(even) td` rule (both are shared across every page via `HTML_STYLE`) and silently lost to it, so the original per-game highlighting never actually took effect until the `tr` was added to match that rule's specificity exactly and win on source order. Every price shown (puck line, total, moneyline) is followed by its devigged implied probability in parens via the shared `devig_pair()` helper — same math as `market_edge`, purely for display, not stored anywhere. The puck-line price itself (e.g. the `+180` next to a `-1.5` line) comes from `odds.home_spread_price`/`away_spread_price`, which `fetch_odds.py` only started capturing once this was built — The Odds API's `spreads` market always included a price per side, it just wasn't being read before. `ML Result` is colored the same way as `Vs. Puck Line` (green win / red loss, via `format_outcome_colored()`); the `Score` cell also shows whether the actual combined score went Over/Under/Push against `total` in parens (e.g. "4–8 (Over)"), comparing against whatever total was last on record for that game — since odds stop updating once a game goes final, this is naturally stable without any special-casing. Every generated page's "Last updated" footer (`generation_timestamp()`) is US Eastern via `zoneinfo`, not UTC — it reads as EDT or EST automatically depending on whether daylight saving is in effect when it runs, rather than a hardcoded label. Re-running for a date replaces that date's *ungraded* `picks_log` rows only, so grading results already recorded aren't clobbered.

`HTML_STYLE` (shared by every page type — picks reports, `policy.html`, `record.html`, `index.html`) sizes the page at `max-width: 1400px` rather than the original 760px, specifically so the 12-column picks table fits on a typical desktop browser without horizontal scrolling — 760px was fine for the simpler early reports but far too narrow once the table grew this wide. `.table-scroll`'s `overflow-x: auto` wrapper (the horizontal-scroll fallback for anything narrower, e.g. a phone) is now scoped off via `@media (min-width: 1400px) { .table-scroll { overflow-x: visible; } }` rather than left always-on, for a reason that isn't just cosmetic: leaving `overflow-x: auto` always active would silently break the sticky table header below it. Setting `overflow-x` to anything but `visible` makes browsers implicitly upgrade the paired, un-set `overflow-y` to `auto` too (per the CSS Overflow spec's rule for mismatched visible/non-visible pairs), which turns that div into its own scroll container — and `position: sticky` sticks to the *nearest* scroll container, not necessarily the page. Inside an always-auto wrapper, `thead th { position: sticky; top: 0; }` would stick to the wrapper's own box (which never independently scrolls, since it isn't height-constrained) instead of the viewport, so the header would silently fail to freeze while scrolling the actual page — the exact kind of silent CSS failure the `tr.game-even`/`tr.game-odd` specificity bug above was. Scoping the scroll wrapper to narrow viewports only keeps it structurally `overflow-x: visible` (a true no-op, not a scroll container) everywhere the horizontal scroll isn't actually needed, which is what lets the sticky header actually freeze on desktop.

The green `<strong class="pick">` highlight is applied independently in each of the three market columns, not just once per game — each column has its own recommendation, computed differently, and they can (and routinely do) disagree:
- **Money Line**: the same overall pick driven by `daily_scores.total_score` (policy.yaml's weighted score) — unchanged from before.
- **Puck Line**: `puck_line_recommendation()` projects this game's scoring margin as the home and away teams' own recent `goal_differential` (from `form_metrics.py`) against each other, with no further weighting, and checks whether that projected margin clears the fixed 1.5-goal line in the favorite's direction — recommending the underdog (+1.5) instead of the favorite (-1.5) when it doesn't. This is a genuinely separate read from Money Line (a team can be the better overall team — and thus the Money Line pick — while still projecting to win by less than 1.5, which recommends betting *against* them on the puck line).
- **Over/Under**: `total_recommendation()` projects the game's combined total as each team's expected goals (the average of its own `goals_for_avg` and the opponent's `goals_against_avg`, both from `form_metrics.py`), summed, and compares that to the market's own total line.
Both are intentionally simple, un-weighted projections (not policy.yaml metrics) — they're answering "does this number clear a fixed market line," a different kind of question than Money Line's "which team scores higher," so they don't belong in the same weighted-sum machinery. Either returns `None` (no highlight on either side) when there isn't enough trailing-game data yet (e.g. a team's first few games of the season) or the projection lands exactly on the market's line.

Only when `target_date` is actually today (`is_today` inside `render_html_report()`), the page also gets an **Est. Winnings** column and a Money Line/Puck Line dropdown above the table — the one piece of client-side JavaScript on the whole site (everything else is pure static HTML). Each pick's rowspan'd winnings cell carries `data-ml`/`data-pl` attributes (its moneyline and puck-line price, via the new `pick_spread_price` field in `build_picks()`), pre-rendered server-side for the default (moneyline) selection via `potential_payout()` — a pure "profit on a $`STAKE` bet if it wins" function, deliberately not `grade.py`'s `moneyline_profit()`, which needs a known win/loss outcome that an ungraded pick doesn't have yet. Switching the dropdown runs inline `updateWinnings()`, which re-reads every `.winnings-cell`'s `data-*` attribute and recomputes — no network round-trip, since this is a fully static page. Gated to today only because it's inherently forward-looking ("if this pick wins, here's the payout") — past dates are already graded, so their real win/loss and actual `profit_10` (on `record.html`/`backtest.py`) is what matters there, not a hypothetical.
11. **`lib/policy_page.py`** — renders `docs/reports/policies/policy.html` straight from `policy.yaml` plus the `metrics` catalog; a read-only reference, not a data output.
12. **`lib/grade.py`** — grades every `picks_log` row whose game is final (`game_state = 'OFF'`, both scores present) and still missing a result: `result` ('win'/'loss'/'push') against the puck-line spread in `spread_at_pick`, `straight_up_result` ('win'/'loss') for whether the picked team won the game outright, and `profit_10` — the $ profit/loss a flat $`STAKE` (currently $10) moneyline bet on the pick (`moneyline_at_pick`) would have made, settled on `straight_up_result` (moneyline bets pay out on who wins the game, not who covers). These are tracked separately because `spread_at_pick`/`moneyline_at_pick` are often `NULL` (no odds fetched that day) — those rows still get a `straight_up_result`. A plain win/loss record doesn't tell you whether picks would have been profitable (a run of favorites can go win-heavy and still lose money), which is what `profit_10` is for — `backtest.py` sums it per `policy_version` for an actual ROI figure. Safe to re-run; only touches rows still missing any of these three. `STAKE` lives in `grade.py` and is imported by `backtest.py`/`record_page.py` rather than redeclared, so changing the bet size is a one-line edit in one place.
13. **`lib/record_page.py`** — renders `docs/reports/record.html`: picks_log's overall straight-up/ATS record and moneyline ROI (reusing `backtest.py`'s `policy_performance()` rather than re-deriving them), plus the same breakdown per `policy_version`. The published, no-terminal counterpart to `backtest.py`'s console output — linked from `docs/index.html` as "Performance record & ROI," guarded the same way as the "Today's Picks" link so a fresh deploy never shows a dead link before the page exists once.
14. **`bin/run_daily.py`** — orchestrates steps 2–13 for one date by inserting `lib/` onto `sys.path` and importing/calling each module's entrypoint function directly (no subprocesses). Since every stage is either an upsert or a full rebuild, there's no "only run what's needed" logic — it just runs everything every time, which is simpler and still cheap. Its schedule fetch uses a `--lookback-days` window (default 3) behind the target date so recently-completed games' final scores get upserted even after they've aged out of being "today," and grading runs right after that fetch so those newly-final scores get graded the same run. `record_page.py` is rebuilt immediately after grading (so it's always current before the "refresh every past report" loop checks whether to link it), and `market_metrics.py` runs even when `ODDS_API_KEY` isn't set, rebuilding from whatever odds snapshots are already on record.
15. **`bin/run_daily_cron.sh`** — cron-safe wrapper around `run_daily.py` for unattended daily runs (absolute paths, sources `.env`, logs to `nhl_toolkit/logs/`).

`lib/arenas.py` is static reference data (lat/lon + IANA timezone per team, keyed by the 3-letter abbrev the NHL API uses), plus `TEAM_NAME_TO_ABBREV`, a reverse lookup built from that same data for feeds (like odds) that identify teams by full name. Note the ARI→UTA relocation: `ARENAS["ARI"]` is aliased to the same record as `ARENAS["UTA"]` so historical pre-2024-25 data still resolves. `ARENAS["UTA"]["team"]` is the current "Utah Mammoth" (their permanent name as of the 2025-26 season) with "Utah Hockey Club" (their 2024-25 inaugural-season placeholder name) kept as an extra `TEAM_NAME_TO_ABBREV` alias. `ARENAS["MTL"]["team"]` is "Montréal Canadiens" *with the accent* — that's the exact spelling The Odds API uses, with the unaccented "Montreal Canadiens" kept as a fallback alias. Both of these are the same failure mode: an exact-match name lookup silently dropped every odds quote for that franchise's entire history (Utah: a stale pre-rename name; Montreal: a missing diacritic) until each was caught by querying The Odds API directly and diffing its `home_team`/`away_team` strings against what was hardcoded here. If a team's odds are mysteriously always missing, suspect this exact failure mode first and verify against the live feed rather than guessing — don't assume `TEAM_NAME_TO_ABBREV`'s spelling is right just because it looks plausible.

`lib/backtest.py` is a standalone, read-only diagnostic (`python lib/backtest.py`, not wired into `run_daily.py`) for tuning `policy.yaml` weights: it correlates each metric's home-minus-away differential against the actual final goal margin across every completed game, and prints `picks_log`'s real straight-up/ATS record *and* moneyline ROI (summed `profit_10` on a flat $10 stake per pick, as a % of total staked) per `policy_version`. It never hardcodes a metric name — it reads whatever rows exist in the `metrics` table, so a future metric (injuries, head-to-head, goalie quality) shows up here automatically the first time something populates its `metric_values`, with zero changes to this file (this is exactly how `market_edge`'s correlation went from `n/a` under the old spread-based computation to a real, non-zero value once it was reworked onto the moneyline — no `backtest.py` changes needed either time). It's purely advisory (never writes to `policy.yaml`); a metric's correlation sign/magnitude is a hint for hand-tuning its weight, not a verdict, especially early in a season when sample sizes are tiny (see `--min-n`). Note `home_ice` always correlates as `n/a`: its home-minus-away differential is definitionally constant (1 for every game), so this particular diagnostic can't say anything about it.

SQLite was chosen deliberately for zero-config local development; the schema is kept plain enough that a future Postgres migration is meant to be a straight port, not a rewrite (see `lib/db.py` docstring).

## Roadmap (not yet implemented)

Per `nhl_toolkit/README.md` and `betting-toolkit-design.md`:

- An `injuries` table (deferred as the messiest data source — likely needs scraping) and injury-derived metrics.
- A cumulative-edge/streaks view over `picks_log` beyond the win/loss/ROI record `lib/record_page.py` now publishes (see Architecture below) — e.g. a running bankroll chart, current streak, best/worst single pick.
- Head-to-head record and starting-goalie quality — the generic `metrics`/`metric_values` schema already supports adding these without touching `score.py` or `lib/backtest.py`, but nothing populates them yet. (`recent_form`/`goal_differential` are now implemented, in `form_metrics.py`.)

Further out, not yet designed — see `betting-toolkit-design.md` section 10: player-level stats sourced from MoneyPuck.com (especially goalie data), which would need a schema step up from today's team-level-only tables; and eventually tracking/placing real bets, a materially different feature from the current paper-trading `picks_log`/grading design.

Don't assume any of this exists — check the actual code before referencing it.
